## Что сделано (итог)

### R5.3 — MCP Tasks extension (`io.modelcontextprotocol/tasks`)

Новый файл `local_coding_agent/tasks.py`:

- `TasksExtension(Extension)` поверх существующего `BoundedWorkerPool`.
- `intercept_tool_call` перехватывает `tools/call` с `name="delegate_code"`:
  - если клиент **заявил** extension в `_meta.clientCapabilities.extensions` →
    атомарный `pool.submit(...)` и возврат flat `CreateTaskResult`
    (`resultType:"task"`, `taskId`, `status`, `createdAt`, `lastUpdatedAt`,
    `ttlMs`, `pollIntervalMs`) **без** вызова `call_next`;
  - иначе → `call_next(ctx)` (обычный синхронный proposal-only путь);
  - невалидные аргументы → `call_next` (синхронный policy failure, не task).
- Методы: `tasks/get` (flat `Task` + `resultType:"complete"`), `tasks/cancel`
  (`pool.cancel` + ack `{"resultType":"complete"}`), `tasks/update` (ack, MVP
  не имеет `input_required`-потока).
- `task_dict()` маппит snapshot pool'а в modern flat Task shape. Task store —
  **in-memory** pool, НЕ durable disk.

Подключение в `mcp_server.build_server(service, enable_tasks=False, max_workers=1,
max_queue=16)`. По умолчанию `enable_tasks=False` → чисто синхронный путь
(обратная совместимость сохранена, существующие тесты не тронуты).

### R5.4 — `apply_proposal` (explicit apply)

- Отдельный tool `apply_proposal(request_id, workspace_ref)` — НЕ поле в
  `delegate_code` (как требует `docs/MCP_DESIGN.md`: нельзя смешивать постановку
  задачи с destructive decision).
- Подтверждение — Multi Round-Trip Request elicitation через `Resolve`/`Elicit`:
  tool принимает `Annotated[ElicitationResult[ApplyConfirmation], Resolve(_resolve_apply)]`.
  `decline`/`cancel`/`confirm=false` → `rejected` без изменений на диске.
- `DelegationService.apply(caller_id, workspace_ref, request_id)`:
  1. находит terminal proposal из idempotency-кэша (`_CachedResult` теперь хранит
     `request` для повторного доступа к `TaskEnvelope`/`workspace_ref`);
  2. только `status == "accepted"` + непустой `patch`;
  3. `check_patch_applies` (revalidate против текущего workspace) →
     `stale_workspace` при расхождении;
  4. `apply_patch` → `run_post_apply_checks` (allowlisted checks) → при failure
     `apply_patch(reverse=True)` rollback;
  5. при неудачном rollback — явный флаг `workspace_modified: true` + risk
     `rollback_failed`, чтобы потребитель не принял модифицированный workspace
     за чистый.

## Проверенные факты SDK (mcp==2.0.0) — важно для следующей модели

1. **SDK Task-типы — старый shape, НЕ то что шлёт современная extension.**
   `mcp.types.CreateTaskResult`, `GetTaskResult`, `Task` помечены "2025-11-25 only":
   у `Task` поле `ttl: int | None` **required**, `poll_interval`, и `CreateTaskResult`
   оборачивает `task: Task` (nested). Современная Tasks extension (SEP-2663,
   repo `modelcontextprotocol/ext-tasks`) шлёт **flat** `CreateTaskResult = Result & Task`
   с `ttlMs`/`pollIntervalMs` и `resultType:"task"`. Поэтому `tasks/get` в тестах
   парсится кастомной flat-моделью, а не `mcp.types.GetTaskResult` (у него `ttl`
   required → ValidationError).
2. **`intercept_tool_call` short-circuit dict с `resultType:"task"` доезжает до
   клиента целиком.** В `ServerRunner._serialize` (runner.py:341-394) для `tools/call`
   при modern-версии и extension-теге `resultType` вне `CORE_RESULT_TYPES` → sieve
   пропускается. Подтверждено эмпирически probe'ом, не на веру.
3. **Client-claim:** `ResultClaim(result_type="task", model=<Result-подкласс с
   `result_type: Literal["task"]`>)`; `resolve` возвращает `CallToolResult`. Либо
   `session.call_tool(..., allow_claimed=True)` и парсить самому.
4. **Resolver-annotations обязаны быть module-level.** SDK делает
   `inspect.signature(fn, eval_str=True)` и eval'ит строки аннотаций в `globals` —
   вложенные классы/имена из локальной области функции дают `NameError` →
   `InvalidSignature`. Поэтому `ApplyConfirmation`/`_resolve_apply` вынесены на
   module-level в `mcp_server.py`.
5. **`Elicit`-resolver подпись:** `def resolve(ctx: Context) -> Elicit[T]` (тип
   `Context` обязателен, иначе `InvalidSignature`); tool-параметр
   `Annotated[ElicitationResult[T], Resolve(resolve)]`.
6. **Client `elicitation_callback` должен быть `async`**, возвращает `ElicitResult`.
   Синхронный → `TypeError: object ElicitResult can't be used in 'await' expression`.
7. **`require_client_extension` поднимает `-32021`** (`MISSING_REQUIRED_CLIENT_CAPABILITY`),
   а НЕ `-32003`, как было зафиксировано в ранних заметках. Код сменился в mcp 2.0.0.
   В моей реализации я не использую `require_client_extension`, а вручную проверяю
   capabilities и делаю sync fallback (по spec: «никогда не возвращай task клиенту,
   который не заявил поддержку»).
8. **`CallToolResult` output schema:** у `delegate_code` output schema = `null`
   (unstructured), поэтому claim-resolver'у не нужно возвращать `structured_content`
   под output-schema. Ранний probe ловил это: при structured tool нужно отдавать
   `structured_content` соответствующий output schema, иначе
   `validate_tool_result` → `RuntimeError`.
9. **`EmptyResult` dumps как `{}`**; на 2026-07-28 пустой результат обязан нести
   `resultType:"complete"` — поэтому мои ack-хендлеры возвращают
   `{"resultType":"complete"}`, а не `EmptyResult`.

## Сомнения (не до конца закрытые решения)

1. **Task store in-memory vs durable.** Я сделал in-memory поверх `BoundedWorkerPool`,
   как и заявлено в MCP_DESIGN («durable store = отдельный gate»). Но реальная
   ценность Tasks (crash/reconnect-устойчивость) требует disk-backed store. Это
   осознанный пробел, а не баг: после рестарта процесса `task_id` теряется.
2. **Capability fallback = sync.** При отсутствии opt-in я возвращаю синхронный
   результат, а не ошибку. Это дружелюбнее к legacy клиентам, но `delegate_code`
   может блокировать event loop дольше, чем клиент ждёт (Ollama минуты). Sync-путь
   не offload'ится в executor — осознанный выбор для local stdio MVP, но для
   production нужно либо offload, либо bounded timeout.
3. **Single-tenant caller id.** `_CALLER_ID = "mcp-stdio"` жёстко один на все
   запросы → idempotency/task pool namespace общий. Для одного прямого stdio-клиента
   ок, для remote HTTP — нет (нужен verified principal → caller id). Задокументировано
   в docstring `mcp_server.py`.
4. **`apply_proposal` доступен и без tasks capability.** Оно не требует Tasks
   extension (elicit — отдельная возможность MRTR), но семантически apply связан с
   proposal, который при async-пути хранится в pool. Сейчас `apply` смотрит только
   idempotency-кэш `DelegationService`, а НЕ pool. Если proposal получен через
   async task (pool), он также есть в service idempotency-кэше (pool вызывает тот же
   `service.delegate`), поэтому `apply` его найдёт. Но связность «task_id → proposal»
   неявная — стоит явно выровнять, если apply должен принимать `task_id` вместо
   `request_id`.
5. **`request_id` vs `task_id` в apply.** `apply_proposal(request_id, workspace_ref)`
   использует `request_id` (idempotency key из `delegate_code`), а не `task_id`
   (job handle из Tasks). Логично (proposal = результат делегирования), но при
   async-потоке клиент знает `task_id`, а не `request_id`. Возможно стоит принимать
   оба или переименовать.

## Неудачи / ошибки по ходу работы

1. **Probe'ы на выброшенной ветке.** Я писал throwaway probe-скрипты в
   `%TEMP%\opencode` (probe_tasks.py, probe2.py, probe_apply.py, probe_tasks_e2e.py,
   probe_apply_e2e.py, probe_apply2.py, probe_apply3.py) и удалил их в конце. В
   коммит они не входят. Полезные выводы из них перенесены в «Проверенные факты SDK».
2. **`InvalidSignature: name 'Annotated' is not defined` / `'ElicitationResult'` /
   `'ApplyConfirmation'`.** Три раунда одной и той же ошибки: я сначала держал
   `apply_proposal` с вложенными классами и локальными импортами. Причина — пункт 4
   выше (SDK eval'ит аннотации в module globals). Исправление: всё на module-level.
3. **`InvalidSignature: Resolver '_resolve_apply' parameter 'ctx' cannot be resolved`.**
   Resolver'у нужен точный тип `ctx: Context`; я сначала писал `ctx` без аннотации,
   потом `ctx: Context` — заработало.
4. **Client `elicitation_callback` sync → async.** Первый вариант callback был
   синхронным, падало `TypeError: object ElicitResult can't be used in 'await'`.
   Исправление: `async def`.
5. **`GetTaskResult` validation error `ttl: Field required`.** Первый вариант
   `tasks/get` парсился через `mcp.types.GetTaskResult` (старый shape, `ttl`
   required) — упало. Вывод: modern flat shape ≠ SDK-тип; парсить кастомной
   flat-моделью.
6. **Тест rollback ловил `risks`, а не `error`.** После рефакторинга `apply`
   (code-review P2-4: сделать result shape консистентным) я перенёс
   `post_apply_check_failed` из `risks` в `error`, а тест не обновил — один красный
   тест, исправил assert.
7. **`FakeModel` vs последовательность ответов.** В apply-тестах я сначала передал
   список из двух ответов в `FakeModel`, который ждёт один response (повторяет его
   вечно) — controller получил tool_calls там, где ждал финальный JSON. Добавил
   `SequenceModel` для многошаговых сценариев.
8. **`require_client_extension` = `-32021`, не `-32003`.** В ранних заметках (план)
   фигурировал `-32003`; фактический код в mcp 2.0.0 — `-32021`. Зафиксировано.
9. **Выброшенный `_handler_result_to_dict` / `_ELICIT_AVAILABLE`.** По ходу писал
   неиспользуемые хелперы и флаги; вычищены в финальной версии.
10. **PonyTail-режим конфликтовал с объёмом работы.** Первоначально был включён
    «lazy»-режим, который толкал к минимализму; пользователь явно его отключил и
    разрешил писать «как получается». Код местами не самый лаконичный — это осознанный
    компромисс, следующая модель может отрефакторить.

## Решение по R6 (fairness / Ollama scheduling)

НЕ реализовано. Логика (согласована с пользователем): на одной GPU Ollama держит
одну модель в VRAM; смена модели строго последовательная. Round-robin «честность»
между model profiles — решение несуществующей на single-GPU проблемы. Запрос с
незагруженной моделью отклоняется/ждёт освобождения слота. При необходимости
round-robin scheduler — отдельный gate (зафиксировано в ROADMAP.md примечанием).
